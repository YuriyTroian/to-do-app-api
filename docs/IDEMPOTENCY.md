# Ідемпотентність операцій запису

Код: [`app/idempotency.py`](../app/idempotency.py), `POST /tasks/` у [`app/crud.py`](../app/crud.py). Тести: [`tests/test_idempotency.py`](../tests/test_idempotency.py).

## Яку проблему це розв'язує

Клієнт надіслав `POST /tasks/`, сервер запис створив, але відповідь не дійшла: таймаут, обрив мережі, перезапуск екземпляра під час масштабування. Клієнт не знає, виконався запит чи ні, тому повторює його, і запис створюється двічі. Під навантаженням це не рідкість: у наших прогонах p99 латентності був 7–9 с, а максимум понад 11 с, тож клієнти з коротким таймаутом повторювали б запити саме тоді, коли сервіс найповільніший.

`POST` не є ідемпотентним за визначенням (на відміну від `GET`, `PUT`, `DELETE`, `HEAD`, `OPTIONS`). Заголовок `Idempotency-Key` робить його безпечним для повтору: клієнт генерує унікальний ключ (наприклад, UUID) на одну логічну операцію й надсилає той самий ключ при кожному повторі.

## Як це працює

1. Запит без заголовка працює як раніше.
2. Перший запит із ключем «захоплює» ключ у Redis командою `SET ... NX` зі станом `processing` (живе 60 с) і виконується.
3. Після успішного запису результат (код і тіло відповіді) зберігається в Redis під ключем `idem:<ключ>` на **24 години**.
4. Повторний запит із тим самим ключем не виконується. Сервер повертає збережену відповідь із заголовком `Idempotent-Replayed: true`.

Інші випадки:

| Ситуація | Відповідь |
|---|---|
| Той самий ключ, інше тіло запиту (порівнюється SHA-256 відбиток) | `422` |
| Той самий ключ, перший запит ще виконується | `409` |
| Виконання впало (наприклад, конфлікт унікального `priority`) | ключ видаляється, клієнт може повторити |
| Redis недоступний | `503` (краще відмовити, ніж створити дубль) |

Працює незалежно від `cache_enabled`: перемикач стосується лише кешу списку, а Redis для ідемпотентності потрібен завжди.

### Ручна перевірка на розгорнутому сервісі

Команди для демонстрації на захисті (PowerShell). Нову версію розгорнуто в ECS (образ перезібрано, `update-service --force-new-deployment`), перевірку виконано 18.11.2026.

```powershell
$u = "http://todo-api-alb-725788838.eu-north-1.elb.amazonaws.com/tasks/"
$h = @{ "Idempotency-Key" = "demo-1" }
$b = '{"title":"idem demo","priority":777001}'
1..2 | ForEach-Object {
  Invoke-WebRequest -Method Post -Uri $u -Headers $h -ContentType "application/json" -Body $b -UseBasicParsing |
    Select-Object StatusCode, Content, @{n="Replayed";e={$_.Headers["Idempotent-Replayed"]}}
}
```

Очікується: обидва `200`, однаковий `id`, у другої відповіді `Replayed = true`, а `GET /tasks/` містить один запис `idem demo`.

**Результат на розгорнутому сервісі** (два однакові `POST` з ключем `demo-1794959695`):

| | Перший запит | Другий запит |
|---|---|---|
| Код | `200` | `200` |
| Заголовок `Idempotent-Replayed` | немає | `true` |
| `id` у відповіді | `5c88e844-0489-416c-9c46-f198bcd941dd` | `5c88e844-0489-416c-9c46-f198bcd941dd` |
| `created_at` | `2026-11-17T23:54:55.789201` | `2026-11-17T23:54:55.789201` |

Тіла відповідей ідентичні, у `GET /tasks/` знайшовся рівно **один** запис із цим `priority`. Той самий ключ з іншим тілом дав `422`. Тестовий запис після перевірки видалено.

## Як поєднується із завданням 6 (черга)

Завдання 6 (асинхронна обробка через чергу) у цьому репозиторії **не реалізоване**, тож це опис того, як ці механізми працюють разом.

У схемі з чергою сервіс кладе повідомлення в чергу й відповідає `202 Accepted`, а окремий обробник виконує запис. Черги зазвичай гарантують доставку «щонайменше один раз», тобто те саме повідомлення може бути доставлене двічі (наприклад, обробник упав до підтвердження). Без захисту це дало б дубль запису.

Ідемпотентність закриває обидва місця, де можливий дубль:
- **клієнт → сервіс:** повтор `POST` з тим самим `Idempotency-Key` не додає друге повідомлення в чергу, а повертає ту саму `202`-відповідь;
- **черга → обробник:** ключ передається в повідомленні, а обробник перед виконанням «захоплює» його в Redis (`SET NX`) і зберігає результат. Повторно доставлене повідомлення впирається в уже виконаний ключ і не пише в базу вдруге.

## Обмеження поточної реалізації

- **Вікно між `commit` і збереженням результату.** Якщо процес упаде після запису в базу, але до `complete()`, ключ лишається в стані `processing` ще до 60 с. Після цього повтор виконається вдруге і створить дубль. Повне вирішення — писати ключ у таблицю бази з `UNIQUE` у тій самій транзакції, що й запис.
- **Redis-заглушка в тестах.** Тести перевіряють логіку застосунку, але не поведінку реального ElastiCache (наприклад, затримки під навантаженням).
