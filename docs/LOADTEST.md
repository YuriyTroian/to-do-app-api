# Навантажувальне тестування

Сценарій: [`loadtest/script.js`](../loadtest/script.js) (k6).

## Профіль «мало записів, багато читань»

Одна ітерація віртуального користувача: 1× `POST /tasks/`, потім 9 читань (`GET /tasks/` ×3, `GET /tasks/{id}` щойно створеного запису ×4, `GET /stats` ×2) з паузою 0,3 с між запитами. Співвідношення запис : читання = 1 : 9.

Фази: наростання 0 → N за 3 хв, стале навантаження N 5 хв, спад до 0 за 2 хв (разом 10 хв).

**Про «дані автора».** У методичці серед читань названо «дані автора». У нашому застосунку немає сутності автора, тому замість цього сценарій викликає `GET /stats` (агрегована статистика), що є окремою операцією читання.

## Запуск

```bash
k6 run loadtest/script.js
k6 run -e BASE_URL=http://<alb-dns> -e VUS=80 loadtest/script.js
```

| Параметр | За замовчуванням | Опис |
|---|---|---|
| `BASE_URL` | ALB поточного розгортання | Адреса сервісу |
| `VUS` (N) | 80 | Користувачі на плато. При 40 CPU піднімався вище порога лише через ≈3 хв плато, при 80 навантаження достатнє, щоб масштабування спрацьовувало усередині плато. Обмеження сценарію: VUS ≤ 99 через унікальний `priority` |

Для збереження підсумку в PowerShell: `k6 run ... | Tee-Object loadtest/run.txt`.

## Чому раніше пропускна здатність була набагато меншою (41 → 9–13 запитів/с)

У перших прогонах пропускна здатність упала з 41,6 до 9–13 запитів/с (дивіться таблицю нижче), і причина спершу не була пояснена. Це не наслідок кешу, бо різниця є і в прогоні без кешу. Причина — ендпоінт `GET /stats`, який виконується двічі за ітерацію. Він завантажував у Python **усю таблицю тричі** (всі, завершені, незавершені записи), тож його вартість росла разом із кількістю рядків, а кожен прогін додає ≈600–8 600 рядків (на момент завершення всіх вимірювань у базі 24 607 записів). Мікробенчмарк на локальній SQLite показав:

| Рядків у таблиці | `/stats` (старий код) | `/tasks/?limit=100` | `/stats` (після виправлення) |
|---|---|---|---|
| 500 | 15,3 мс | 6,6 мс | 3,3 мс |
| 2 000 | 50,2 мс | 6,1 мс | 3,9 мс |
| 5 000 | 119,6 мс | 5,8 мс | 6,4 мс |

Вартість `/stats` росла лінійно (у 8 разів при 10-кратному зростанні таблиці), а вартість списку не змінювалась. На Fargate із 0,25 vCPU, значно слабшому за ноутбук, ця різниця критична: два виклики `/stats` на ітерацію з'їдали більшість CPU задачі.

Виправлення: `/stats` тепер — один агрегатний SQL-запит (`COUNT(*)` із `FILTER`), вартість не залежить від розміру таблиці. На AWS після виправлення `/stats` разом із кешем за TTL (прогін 18.11 о 15:08, VUS = 40) пропускна здатність склала 43,6 запиту/с проти 9,4–13,5 раніше при тих самих VUS, хоча таблиця була вже більшою (≈5 000 рядків). Окремо внесок `/stats` на AWS без кешу не вимірювався.
