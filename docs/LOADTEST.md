# Навантажувальне тестування

Сценарій: [`loadtest/script.js`](../loadtest/script.js) (k6).

## Профіль «мало записів, багато читань»

Одна ітерація віртуального користувача: 1× `POST /tasks/`, потім 9 читань (`GET /tasks/` ×3, `GET /tasks/{id}` щойно створеного запису ×4, `GET /stats` ×2) з паузою 0,3 с між запитами. Співвідношення запис : читання = 1 : 9.

Фази: наростання 0 → N за 3 хв, стале навантаження N 5 хв, спад до 0 за 2 хв (разом 10 хв).

## Запуск

```bash
k6 run loadtest/script.js
k6 run -e BASE_URL=http://<alb-dns> -e VUS=40 loadtest/script.js
```

| Параметр | За замовчуванням | Опис |
|---|---|---|
| `BASE_URL` | ALB із лабораторної 1 | Адреса сервісу |
| `VUS` (N) | 40 | Кількість користувачів на плато; при 40 CPU ECS-задач виходить на ≈100 % і масштабування спрацьовує (обмеження сценарію: VUS ≤ 99 через унікальний `priority`) |

Для збереження підсумку в PowerShell: `k6 run ... | Tee-Object loadtest/run.txt`.

## Підсумковий звіт

Усі прогони: VUS = 40, 10 хвилин, ті самі параметри сценарію.

| Показник | 16.11, 20:32 UTC (до кешу) | 17.11, 20:41 UTC (кеш, таймаут 0,5 с — кеш не працював) | 17.11, 21:37 UTC (з кешем) | 17.11, 22:32 UTC (без кешу) |
|---|---|---|---|---|
| Запитів | 12 510 | 7 570 | 5 666 | 8 150 |
| Ітерацій | 1 251 | 757 | 565 | 815 |
| Запитів/с | 41,6 | 12,6 | 9,4 | 13,5 |
| Частка помилок | 0,00 % | 0,02 % | 0,00 % | 0,03 % |
| p50 | 489,66 мс | 1,79 с | 2,69 с | 1,64 с |
| p95 | 1,18 с | 5,55 с | 6,99 с | 5,10 с |
| p99 | 1,47 с | 7,81 с | 9,27 с | 7,09 с |
| Максимум | 2,2 с | 11,5 с | 14,2 с | 12,19 с |
| Пік екземплярів | 2 | 2 | 3 | 3 |

**Чому 16.11 і 17.11 відрізняються так сильно.** Прогін 16.11 виконувався на іншій версії застосунку (без кешу, без Redis), і вона дала вдвічі більшу пропускну здатність при менших затримках. Різниця між версіями не досліджувалась, тому порівнювати 16.11 з 17.11 не можна. Для висновків про кеш використовуємо лише прогони 17.11 з кешем і без нього.

**Частка помилок.** Усі прогони мають 0–3 невдалих запити з 5 000+. На графіку 5xx ALB за прогін 17.11 (20:41) даних немає, тобто відповідей 5xx не було, тож помилки, найімовірніше, стались на боці клієнта (таймаути k6 на найповільніших запитах). Причину не перевіряли.

**Порогове значення сценарію** `http_req_failed < 1 %` виконано в усіх чотирьох прогонах.

Порівняння «з кешем / без кешу» див. [CACHE.md](CACHE.md).
